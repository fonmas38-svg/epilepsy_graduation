# التدقيق الهندسي والأمني للنظام — 28 أكتوبر 2026

- **النسخة المفحوصة:** `b8eb691`.
- **النطاق:** FastAPI، طبقة البيانات والترحيلات، Flutter، لوحة React، محاكي الجهاز، ومسارات البحث والاستدلال.
- **نوع العمل:** قراءة التنفيذ، تشغيل الاختبارات، وإعادة إنتاج أعطال على بيانات وهمية وتخزين مؤقت. لم تُعدَّل ملفات التنفيذ، ولم تُستخدم قاعدة الإنتاج أو تُرسل إشعارات حقيقية.
- **دلالة الأدلة:** «أُعيد إنتاجه» تعني تجربة محلية؛ «ثابت من المصدر» تعني مراجعة الشيفرة؛ «مشروط بالنشر» يحتاج فحص البيئة الفعلية.
- **الأولوية:** `P0` إجراء عاجل/مانع للإطلاق؛ `P1` خطر مرتفع؛ `P2` إصلاح تشغيلي أو وظيفي مهم. هذه أولوية هندسية وليست درجة CVSS أو شهادة طبية.

## 1. الخلاصة التنفيذية

النظام يحتوي أساسًا برمجيًا مفيدًا لمشروع تخرج: أدوار وصلاحيات، تخزين SQL، ترحيلات، outbox للتنبيهات، اختبارات، ونماذج عصبية قابلة للتحميل في الخادم. لكنه **غير جاهز للاعتماد عليه في مراقبة مرضى حقيقيين أو ضمان التنبؤ المبكر بالنوبات** بصورته الحالية.

الأسباب الأهم:

1. قيمة مفتاح Supabase سرية مضمَّنة في ملف متتبع في Git، وحسابات تجريبية تُنشأ حتى في وضع الإنتاج.
2. مسار ربط المرافق يسمح بربط حساب مدير، ثم يسمح للمريض بتعطيل ذلك الحساب.
3. استقبال الجهاز لنافذة عالية الخطورة لا يكمل وحده حفظ التقييم والتنبيه وطابور الإرسال.
4. الهاتف يخلط بعض سلوكيات المحاكاة مع ملفات مرضى حقيقيين، ويستطيع الاحتفاظ بتوقع قديم بعد إشارة غير صالحة.
5. أخطاء في عقود API والمزامنة والتزامن تؤدي إلى بيانات غير محفوظة أو عمليات تبدو ناجحة محليًا ولا تصل إلى الخادم.
6. الأدلة البحثية المتاحة لا تثبت حساسية سريرية أو تنبؤًا استباقيًا صالحًا للاستخدام الطبي.

**نجاح اختبارات المشروع لا ينفي هذه العيوب:** أُعيد إنتاج عدة عيوب خارج السيناريوهات التي تغطيها الاختبارات الحالية.

## 2. كيف يعمل النظام فعليًا؟

| المكوّن | التنفيذ الحالي | الملاحظة الأساسية |
|---|---|---|
| الحسابات | JWT، أدوار `admin/doctor/patient/caregiver/device`، ربط الطبيب والمرافق بالمريض | توجد ضوابط مهمة، لكن التحقق من الأدوار غير مكتمل في أحد مسارات الربط |
| الخادم | FastAPI وSQLAlchemy وAlembic، مع SQLite أو PostgreSQL | وجود دعم PostgreSQL لا يعني أن النشر الحالي عليه اختُبر في هذه المراجعة |
| الجهاز | `/device/ingest` ← `DeviceHub` ← تجميع 262 عينة ← المصنف | الحالة والعينات والتسلسل في ذاكرة العملية؛ الحفظ الدائم والتنبيه غير متصلين بهذا المسار كاملًا |
| الهاتف | Flutter، تخزين محلي، خدمات مراقبة ومزامنة وبيانات رعاية | Android/iOS يستخدمان SQLCipher، لكن توجد بيانات حساسة أخرى في SharedPreferences |
| التنبيهات | حفظ alert مع outbox في المعاملة نفسها عند استعمال `cloud_store`، ثم عامل يرسل عبر FCM أو stub | هذه نقطة قوة فعلية، لكنها لا تغطي تلقائيًا كل مسارات توليد الخطر |
| الإدارة | React/Vite، JWT في localStorage، تقديم SPA من FastAPI | تتصادم بعض روابط SPA مع مسارات API؛ ونقل التوكن عبر URL غير آمن |
| الذكاء الاصطناعي | نماذج عصبية في الخادم، وقواعد تجريبية في الهاتف | ليسا المحرك نفسه، ووجود أوزان ONNX لا يعني تشغيلها في الهاتف |

المساران الأساسيان حاليًا:

```text
الجهاز → /device/ingest → DeviceHub → استدلال → حالة في الذاكرة
                                               ↓
                                      polling من تطبيق الهاتف
                                               ↓
                               منطق التنبيه/المزامنة في العميل

الهاتف → /cloud/sync → reading + assessment + alert + outbox
                                                  ↓
                                              عامل FCM
```

الهدف الصحيح لمسار المراقبة المستقلة هو:

```text
الجهاز → تحقق وهوية وتسلسل وجودة إشارة → استدلال
      → معاملة واحدة لحفظ النافذة والتقييم والحدث وoutbox
      → عامل تسليم → إيصال/إقرار/تصعيد
```

لا ينبغي أن يكون فتح شاشة المريض في الهاتف شرطًا لإنشاء حدث خطر صادر عن الجهاز.

## 4. الموانع العاجلة — P0

### F01 — قيمة سرية داخل ملف متتبع في Git

**ثابت من المصدر وGit:** يحتوي `backend/deploy/inspect_and_sync.py:13` قيمة افتراضية بصيغة مفتاح Supabase سري للمتغير `SUPABASE_SERVICE_ROLE_KEY`. الملف متتبع، وتاريخه يتضمن الالتزام `c00bfcf`.

**ما لم يُختبر:** صلاحية المفتاح الحالية، امتيازاته الفعلية، أو وصول طرف خارجي إليه. لم يُستخدم للاتصال بالخدمة، ولا تُعاد كتابة قيمته في هذا التقرير.

**الإجراء:** التعامل معه كمكشوف حتى يثبت إبطاله: إبطال/تدوير المفتاح، مراجعة سجل استعماله، إزالة القيمة الافتراضية، وإلزام تحميل السر من مخزن أسرار. تنظيف تاريخ Git إن لزم إجراء تكميلي وليس بديلًا للتدوير. أضف فحص محتوى للأسرار؛ فحص أسماء الملفات وحده لا يكتشف هذه الحالة.

وجود ملفات `.env` أو مفتاح Firebase محلي ضمن `.gitignore` لا ينفي وجود سر داخل ملف Python متتبع. ولا تعني هذه النتيجة أن الملفات المحلية المتجاهلة ثبت تسريبها إلى Git.

### F02 — حسابات العرض التجريبي تُنشأ في الإنتاج

**أُعيد إنتاجه:** بعد تشغيل محلي مع `APP_ENV=production` وبيانات اعتماد مدير اختبار، أُنشئت حسابات الطبيب والمريض والمرافق التجريبية، ونجح تسجيل الدخول بحساب الطبيب التجريبي وكلمة مروره الافتراضية.

**السبب:** `seed_admin()` يستدعي `seed_demo_accounts()` ما لم يوجد `PYTEST_CURRENT_TEST`؛ لا يوجد شرط يمنعه في الإنتاج. لذلك تخفي بيئة pytest العادية هذا السلوك بدل اختباره.

**المراجع:** `backend/app/users_store.py:338` و`:379`، `backend/app/main.py:96`.

**الإصلاح:** حصر seeding التجريبي في profile تجريبي صريح؛ رفضه في الإنتاج؛ ومعالجة الحسابات التي سبق إنشاؤها. أضف اختبار startup في subprocess دون متغيرات pytest، لا اختبار دالة معزولة فقط.

### F03 — ربط مرافق من دور آخر يتيح تعطيل مدير النظام

**أُعيد إنتاجه:** إنشاء مريض بواسطة طبيب مع اسم مستخدم مدير موجود باعتباره `caregiver_username` نجح بـ `201`. ثم نجح طلب المريض إلى `/patient/caregivers/{admin_id}/disable` بـ `200`، وأصبحت قيمة `disabled` للمدير صحيحة فعلًا.

**السبب:** يعاد استخدام الحساب الموجود دون التحقق من دوره؛ ومسار التعطيل يتحقق من وجود الرابط ثم يغيّر حالة الحساب العامة.

**المراجع:** `backend/app/routers/accounts.py:648` و`:828` و`:840`.

**الإصلاح:** تحقق مركزي من دور المريض والمرافق عند الربط، ومن الدور والصلاحية عند كل تعديل؛ تنظيف الروابط غير الصحيحة الموجودة. ينبغي فصل «إيقاف علاقة المرافق بمريض» عن «تعطيل حساب المرافق عالميًا»، حتى لا يؤثر مريض في علاقات المرافق مع مرضى آخرين.

هذه ليست نتيجة استغلال على خادم حي؛ لكنها سلسلة تجاوز صلاحيات مؤكدة على التنفيذ المحلي.

### F04 — مسار الجهاز لا ينتج تنبيهًا دائمًا مستقلًا عن الهاتف

**أُعيد إنتاجه:** أُرسلت نافذة 262 عينة صُنفت `high_risk` إلى `/device/ingest`. كانت النتيجة: **صفر قراءات محفوظة، صفر تقييمات، صفر تنبيهات، وصفر عناصر outbox جديدة** للمريض التجريبي.

**السبب:** المسار يستدعي `DeviceHub.ingest()` ويعيد النتيجة؛ لا يستدعي حفظ حزمة المراقبة وإنشاء الحدث. وجود outbox صحيح في مسار آخر لا يصلح هذه الفجوة.

**المراجع:** `backend/app/routers/device.py:131`، `backend/app/device_hub.py:65`، وقارن مع `backend/app/cloud_store.py:178`.

**الإصلاح:** جعل الخادم مالك الحدث: بعد التحقق والاستدلال، يحفظ النافذة والتقييم والتنبيه وoutbox في معاملة واحدة، بهوية حدث مستقرة وسياسة suppression/cooldown على مستوى الخادم. اختبر وصول الحدث إلى مرسل وهمي دون تشغيل أي تطبيق هاتف.

## 5. عيوب مرتفعة الأولوية — P1

### F05 — كلمة المرور محفوظة نصيًا لتسجيل الدخول بالبصمة

**أُعيد إنتاجه:** `enableForUser()` يخزن كلمة المرور مرتين في SharedPreferences. واستدعاء `disableForUser()` يحذف النسخة الخاصة بالمستخدم لكنه يترك نسخة `biometrics_bound_password`.

**المرجع:** `mobile/lib/services/biometric_service.dart:147` و`:169`.

**الإصلاح:** لا تحتفظ بكلمة مرور الحساب لإعادة إرسالها. استخدم اعتماد جلسة قابلًا للإلغاء ومقيدًا بخزنة النظام وسياسة المصادقة الحيوية، وامسح مفاتيح التخزين القديمة في ترحيل. تشفير قاعدة SQLCipher لا يحمي كلمات المرور المخزنة خارجها.

### F06 — بيانات مريض حقيقية من الكاش تصبح متاحة لحساب تجريبي

**أُعيد إنتاجه مع `DEMO_MODE=false`:** تطبيق جلسة طبيب بملف مريض وهمي يمثل بيانات حقيقية، ثم تسجيل الخروج، ثم الدخول كمرافق تجريبي، أبقى المريض ضمن `accessiblePatients()`.

**السبب:** `signOut()` لا يمسح كاش المرضى؛ `signInDemo()` يربط هوية العرض بكل مفاتيح الكاش. كما أن fallback لبيانات الاعتماد التجريبية في AppState ليس محصورًا بوضوح في build تجريبي.

**المراجع:** `mobile/lib/services/auth_service.dart:55` و`:145` و`:151`، `mobile/lib/providers/app_state.dart:627`.

**الإصلاح:** فصل مساحة بيانات كل مستخدم/بيئة، إزالة fallback التجريبي من الإصدار الحقيقي، ومسح أو قفل الكاش عند الخروج مع مراعاة outbox غير المرسل. لا تستخدم «إظهار كل الكاش» بديلًا لعدم وجود روابط مصرح بها.

### F07 — توليد قياسات اصطناعية داخل سياق مرضى حقيقيين

**أُعيد إنتاجه:** `MonitoringService.start()` أنشأ قراءة وتقييمًا لمريض عند استدعائه في جلسة طبيب؛ المصدر الافتراضي هو `SignalSource.simulator`. `AppState.selectPatient()` يستدعي هذا المسار دون شرط الدور. كذلك يزرع `_seedPatientTelemetry()` baseline صناعيًا إذا لم يجد سجلًا محليًا، دون بوابة demo صريحة.

**المراجع:** `mobile/lib/services/monitoring_service.dart:65` و`:106`، `mobile/lib/providers/app_state.dart:789` و`:1073`، `mobile/lib/core/config.dart:29`.

**الإصلاح:** المراقبون يقرأون البيانات ولا يولدونها؛ المحاكاة في بيئة ومرضى منفصلين؛ تخزين `source/provenance` للقياسات والتقييمات؛ وعدم تحويل «لا توجد بيانات» إلى `stable` بثقة مصطنعة. الافتراضي الآمن للإصدار الحقيقي ليس المحاكي.

### F08 — إشارة غير صالحة تترك توقعًا قديمًا وتولد pre-alert جديدًا

**أُعيد إنتاجه:** بعد توقع إيجابي قديم، أُعيدت إشارة EEG غير صالحة، مع `watch` وثقة صفر ولا توقع جديد. بقي `latestPrediction` القديم، واستُدعيت callback لتنبيه مبكر جديد.

**السبب:** `_applyPrediction(null)` لا يمسح الحالة؛ والاستعادة تفعل الشيء نفسه؛ وشرط التنبيه لا يفرض صلاحية التقييم وحداثته ومطابقة نافذته. كما لا تُعزل كل حالة التوقع والتاريخ بوضوح عند تغيير المريض.

**المراجع:** `mobile/lib/services/monitoring_service.dart:95` و`:139` و`:181` و`:304`.

**الإصلاح:** ربط كل توقع بـ `patient_id/window_id/observed_at/valid_until`؛ مسحه عند إشارة غير صالحة أو تبديل السياق؛ ومنع التصعيد إذا كانت الجودة غير مقبولة أو البيانات قديمة. اختبر انقطاع الإشارة وتبديل المريض، لا قيم الاحتمال وحدها.

### F09 — حالة اتصال الجهاز لا تنتهي صلاحيتها

**أُعيد إنتاجه:** بعد استقبال عينات، بقي `/device/status` يعيد `connected=true` عند تقديم الساعة يومًا كاملًا دون أي عينة جديدة.

**المراجع:** `backend/app/device_hub.py:153` و`:189` و`:206`.

**الإصلاح:** اشتقاق الاتصال من `last_seen` وTTL؛ فصل `connected` عن `fresh/usable`؛ عرض عمر آخر عينة وسبب عدم صلاحية التقييم. هذا وصف خاطئ لاستجابة API؛ لم يُختبر كل تمثيل له في واجهات الأجهزة الحقيقية.

### F10 — إنشاء مريض ببيانات سريرية يفشل بعد حفظ حساب جزئي

**أُعيد إنتاجه:** إنشاء مريض مع تشخيص/هاتف أعاد `500`، لكن المستخدم بقي محفوظًا وغير موجود في جدول إسناد الطبيب.

**السبب:** استدعاء `cloud_store.update_patient()` غير الموجودة بعد حفظ المستخدم وقبل الإسناد؛ كما أن العملية ليست معاملة واحدة تشمل الحساب والملف والروابط.

**المرجع:** `backend/app/routers/accounts.py:612` و`:637`.

**الإصلاح:** استخدام واجهة المتجر الصحيحة، وتجميع العملية في خدمة/معاملة واحدة. أضف اختبارًا يثبت عدم وجود حساب جزئي إذا فشل أي جزء، وأداة مراجعة للحسابات المتضررة قبل الإصلاح.

### F11 — `/cloud/sync` يقبل بيانات سريرية غير صالحة ويغير اسم المريض

**أُعيد إنتاجه:** قُبلت قراءة بتوقيت غير قابل للتحليل ونبض سالب، وتقييم بتصنيف مجهول وثقة خارج المجال؛ وأُعيد `200`. كما استُبدل الاسم المحفوظ بمعرّف المريض.

**السبب:** `reading/assessment/alert` من نوع `dict` غير محدد؛ وكل sync يمرر `patient_profile={"name": patient_id}`.

**المراجع:** `backend/app/routers/cloud_dataset.py:24` و`:100` و`:110`.

**الإصلاح:** مخططات Pydantic صريحة، تحقق من الوحدات والتوقيت والهوية والمجالات وطول الإشارات، وفصل SOS عن قراءة فسيولوجية مصطنعة. لا تُحدّث الاسم في مزامنة القياسات، وميّز التقييم المحلي عن التقييم الصادر من محرك الخادم.

### F12 — المزامنة المتأخرة تعيد الحالة الحالية إلى الماضي

**أُعيد إنتاجه:** إضافة تقييم `stable` يعود إلى الأمس بعد تقييم `high_risk` حديث غيّرت `currentStatus` إلى stable.

**المرجع:** `backend/app/cloud_store.py:125`، خصوصًا التحديث عند `:136`.

**الإصلاح:** حفظ الحدث التاريخي دون تغيير projection الحالة الحالية إلا إذا كان أحدث وفق توقيت مُتحقق منه وترتيب حاسم للتعادل؛ لا تستخدم ترتيب الإدراج بديلًا لزمن القياس. راجع ترتيب السجلات والتقارير أيضًا.

### F13 — واجهات رعاية في الهاتف بلا مقابل في الخادم

**أُعيد إنتاجه:** طلبات الموارد التالية أعادت `404`: جهات الطوارئ، البطاقة الطبية، المحفزات، الموافقات، سجلات النوبات، والملاحظات السريرية.

**المرجع:** `mobile/lib/services/care_service.dart:16`–`:26`، مقابل الراوترات المسجلة في `backend/app/main.py:142`.

**الإصلاح:** جدول قدرات API واضح؛ تنفيذ الموارد مع RBAC أو تعطيل واجهاتها غير المكتملة والإفصاح عن أنها محلية فقط. وجود واجهة وSQLite لا يثبت أن مشاركة البيانات مع الطبيب تعمل.

### F14 — طلب 404 واحد يمنع إقرارات تنبيه صحيحة بعده

**أُعيد إنتاجه:** عنصر outbox لجهة طوارئ غير مدعومة منع حتى محاولة إرسال acknowledgment صالح يأتي بعده.

**السبب:** `CareService.flushOutbox()` يوقف الحلقة عند `notFound`، وافتراض التعليق بأن كل العناصر التالية ستفشل غير صحيح لأنها تستخدم endpoints مختلفة.

**المرجع:** `mobile/lib/services/care_service.dart:734` و`:762`.

**الإصلاح:** عزل الفشل الدائم بحسب المورد/المسار، dead-letter قابلة للمراجعة، وإعادة محاولة الأخطاء العابرة مع backoff. الحفاظ على الترتيب داخل المورد عند الحاجة، دون حجز إقرارات التنبيهات خلف ميزة غير منشورة.

### F15 — التقييمات غير الحرجة أثناء عدم الاتصال لا تُرسل عند العودة

**أُعيد إنتاجه:** حُفظ تقييم محليًا أثناء offline، ثم أرسلت إعادة الاتصال القراءة فقط مع `assessment=null` وعلَّمت القراءة متزامنة.

**المراجع:** `mobile/lib/services/sync_service.dart:47` و`:292`.

**الإصلاح:** outbox لحزمة القراءة والتقييم لكل حدث، لا للإنذارات وحدها؛ مع هوية مستقرة وإقرار حفظ من الخادم. افصل حالة مزامنة كل كيان أو حزمة بدل استنتاج مزامنة التقييم من مزامنة القراءة.

### F16 — فقد وصفة عند تحديثين متزامنين

**أُعيد إنتاجه بتداخل منضبط:** نجح استدعاءان لإنشاء وصفتين، لكن بقيت وصفة واحدة فقط محفوظة.

**السبب:** قراءة قائمة prescriptions من JSON، ثم إلحاق عنصر، ثم استبدال القائمة كاملة، خارج معاملة تقفل القراءة والكتابة. upsert صف المريض لا يمنع lost update في محتوى JSON.

**المراجع:** `backend/app/routers/prescriptions.py:55` و`:89`، `backend/app/cloud_store.py:49`.

**الإصلاح:** جدول مستقل للوصفات مع معرفاتها وسجل تعديلات؛ أو optimistic concurrency بإصدار ورفض التعارض، أو قفل صف داخل معاملة إذا ظل JSON مستخدمًا. لا تُرجع نجاحًا قبل تحقق الحفظ المطلوب.

### F17 — الحكم السريري على التنبيه يُرفض بسبب المنطقة الزمنية

**أُعيد إنتاجه في العميل والخادم:** `Adjudication.toApiJson()` يحول `DateTime` محليًا دون timezone، والخادم يعيد `422: occurred_at must include a timezone`.

**المراجع:** `mobile/lib/models/care_models.dart:595` و`:601`، `backend/app/routers/clinical.py:63`، `backend/app/schemas.py:29`.

**الإصلاح:** إرسال UTC صريح باستخدام `toUtc().toIso8601String()`، وتوحيد هذه القاعدة في بقية نماذج الرعاية. احتفظ بصرامة التحقق في الخادم بدل إزالتها.

### F18 — انتهاء JWT الجهاز لا يشغّل مسار التجديد في المحاكي

**أُعيد إنتاجه:** توكن جهاز منتهي أعاد `403` من `/device/ingest`. وعند محاكاة هذه الاستجابة، لم يحاول العميل تجديد التوكن لأنه يجدد فقط عند `401`.

**المراجع:** `backend/app/routers/device.py:83` و`:90`، `partners/hardware-sim/sim_client.py:191`.

**الإصلاح:** التمييز بين فشل المصادقة `401` والمنع بالصلاحيات `403`، أو عقد خطأ آلي صريح. اختبر جلسة نقل تتجاوز عمر JWT وإعادة الاتصال، وليس دفعات قصيرة فقط.

### F19 — حد الطلبات الافتراضي يتعارض مع معدل النقل المعلن

**حساب واختبار limiter محلي:** 32 عينة للدفعة عند 256 Hz تعني 8 طلبات/ثانية، أي **480 طلبًا/دقيقة**. الحد الافتراضي للإنتاج **120/دقيقة** للمفتاح نفسه؛ سمح الاختبار بـ120 فقط من 480 طلبًا محاكى.

**المراجع:** `partners/hardware-sim/sim_client.py:41` و`:210`، `backend/app/settings.py:54`، `backend/app/middleware.py:49` و`:77`.

**الحدود:** الاختبار لا يقيس شبكة حقيقية؛ زمن الشبكة والاستدلال قد يخفض المعدل، لكن المطلوب المستمر يظل غير متوافق مع الميزانية الافتراضية.

**الإصلاح:** حصص منفصلة حسب الجهاز/الهوية والمسار، batching يحقق معدل العينات المطلوب، backpressure وحفظ/retry للدفعات. لا ترفع الحد العام عشوائيًا أو تلغِ الحماية.

### F20 — نقل JWT لوحة الإدارة داخل URL

**ثابت من المصدر:** الهاتف يبني `?token=...`، واللوحة تقرأ التوكن وتخزنه في localStorage ثم تنظف العنوان.

**المراجع:** `mobile/lib/features/admin/admin_home_screen.dart:159`، `admin-dashboard/src/context/AuthContext.jsx:13`.

**الخطر:** الطلب الأول قد يصل إلى سجلات البروكسي/الخادم وأدوات التتبع؛ تنظيف URL لاحقًا لا يزيل ذلك. localStorage يزيد أثر أي XSS مستقبلية؛ لم يُثبت وجود XSS أو تسريب خارجي فعلي هنا.

**الإصلاح:** رمز SSO قصير العمر، أحادي الاستخدام، يُستبدل بجلسة آمنة، مع cookies مناسبة `HttpOnly/Secure/SameSite` وضوابط CSRF عند استخدامها؛ لا تمرر bearer طويل الصلاحية في query string.

### F21 — عقد عرض إشعارات FCM لا يحافظ على هوية الحدث والمريض

**ثابت من المصدر؛ لم يُختبر FCM حي:** الخادم يرسل `patient_id/alert_id`، لكن callback الهاتف تختزل الرسالة إلى عنوان ونص. AppState ينشئ معرفًا جديدًا من الوقت ويستخدم UID المستخدم الحالي بدل patient_id الأصلي. كذلك يرشح العرض بحسب المريض النشط وحده، لا مجموعة المرضى المخولين، ولا يرفض تلقائيًا الرسائل عندما يكون السياق النشط null.

**المراجع:** `backend/app/notification_delivery.py:86`، `mobile/lib/services/notification_service.dart:71`، `mobile/lib/providers/app_state.dart:488`.

**الخطر:** إقرار مرتبط بهوية غير أصلية، أو إسقاط عرض تنبيه لمريض آخر تابع للطبيب، أو عرض رسالة متأخرة بعد الخروج حسب ظروف الإرسال. هذه مخاطر مستنبطة من الجسر البرمجي، لا إثبات تسليم فعلي.

**الإصلاح:** كائن إشعار موحد يحمل هوية الحدث والمريض، تحقق من الجلسة ومجموعة صلاحياتها، وجلب الحدث الأصلي قبل الإقرار. اختبر الحسابات المتعددة، تبديل المرضى، foreground/background والخروج offline.

### F22 — إعدادات المصادقة الحيوية الأصلية غير مكتملة

**ثابت من المصدر ومقارنة بمتطلبات الحزمة المثبتة:** `MainActivity` يرث `FlutterActivity` بينما `local_auth_android` يحتاج `FlutterFragmentActivity`. لا يوجد تصريح `USE_BIOMETRIC` صريح في manifest المصدر، ولا `NSFaceIDUsageDescription` في iOS.

**المراجع:** `mobile/android/app/src/main/kotlin/com/epilepsy/monitor/epilepsy_monitor/MainActivity.kt:5`، `mobile/android/app/src/main/AndroidManifest.xml`، `mobile/ios/Runner/Info.plist`.

**الإصلاح:** استكمال إعدادات الحزمة، فحص merged manifest، واختبار بصمة/Face ID على أجهزة فعلية. غياب التصريح من ملف المصدر وحده ليس تقريرًا عن merged manifest الذي لم يُبنَ ويفحص هنا.

## 7. تقييم الذكاء الاصطناعي والتنبؤ

### ما ثبت وما لم يثبت

- **ثبت وجود استدلال عصبي في الخادم:** تحميل النموذج الحالي نجح، والمحرك النشط محليًا `cnn_lstm_fusion`؛ لا يصح القول إن النظام كله مجرد شروط أو إن ملفات الأوزان لا تُستخدم مطلقًا.
- **ثبت أن الهاتف لا يشغل ONNX في `EdgeModelService`:** `initialize()` فارغة و`infer()` حسابات وقواعد مكتوبة يدويًا. الشيفرة تصرح `model_executed=false` و`prediction_source=simulated_heuristic`. المرجع `mobile/lib/services/edge_model_service.dart:7` و`:16` و`:78`.
- **Dataset B في البرنامج الحالي صناعية:** `research/train_seizure_cloud.py:150` يولد الإشارات عشوائيًا وبتركيب موجات. لا تزال مقدمة الملف عند `:18` و`:24` تحتوي وصفًا سريريًا وادعاء حساسية أكبر من 97% يناقضان حدود التجربة المعلنة داخل الدالة.
- **الأدلة المحلية لا تبرهن forecasting:** ملفا Bonn المفحوصان متطابقان، موسومان بمهمة كشف النوبة، ولا توجد ملفات EDF متصلة داخل مجلد البحث المحلي. عدم وجودها محليًا لا يثبت عدم وجود تجربة خارج المستودع، لكنه يمنع التحقق منها هنا.
- **تصحيح برنامج التدريب لا يصحح الأوزان القديمة بأثر رجعي:** مسارات التقييم الحالية تتضمن فصل المجموعات وضبط العتبة على validation، وهذه تحسينات جيدة. لكن لم يُثبت أن المصدر الحالي هو الذي أنتج كل الأوزان والنتائج المحفوظة؛ ولم تُنفذ إعادة تدريب أو تجربة سريرية جديدة.

المراجع الداعمة: `backend/app/ml/classifier.py:325`، `research/scripts/evaluate_holdout.py:56`، `research/scripts/train.py:187`، `docs/MODEL_ARTIFACT_AUDIT.json` و`docs/PREDICTION_READINESS_AR.md`.

### الفرق الذي يجب عرضه بوضوح

**Detection**: هل النافذة الحالية تحتوي نشاطًا مرتبطًا بالنوبة؟

**Forecasting**: هل ستبدأ نوبة بعد النافذة الحالية ضمن أفق محدد، دون تسرب من فترة النوبة أو بيانات المريض إلى الاختبار؟

نجاح الأول لا يثبت الثاني. كما أن تحويل score تجريبي إلى «عدد دقائق متبقية» لا يثبت وجود نموذج صالح لتقدير زمن بدء النوبة. ينبغي منع اللغة الجازمة والعد التنازلي غير المعاير في واجهة موجهة لمستخدم حقيقي.

### الأدلة المطلوبة قبل أي ادعاء سريري

1. تسجيلات مستمرة ومواعيد بداية النوبات موثقة، وتعريف SPH/SOP وpreictal/postictal وفترات الاستبعاد.
2. فصل مرضى حقيقيين بين train/validation/test، مع حماية من تسرب النوافذ المتداخلة؛ معرف التسجيل ليس تلقائيًا معرف مريض مستقل.
3. تجميد preprocessing والوحدات والأقطاب والقنوات ومعدل العينات ونسخة البيانات والمصدر وهاش الأوزان.
4. ضبط العتبة على validation فقط؛ اختبار خارجي مستقل؛ تقييم على مستوى الأحداث، بما فيه الإنذارات الكاذبة/ساعة، حساسية النوبات، زمن الإنذار، ونسبة الوقت داخل حالة التحذير، مع فواصل ثقة.
5. اختبار الانقطاع والتشويش والحركة والقنوات المفقودة والمعايرة، ثم دراسة مستقبلية بإشراف سريري وموافقات مناسبة.

إلى حين ذلك، الوصف الدقيق هو **نموذج بحثي/تجريبي للمراقبة والكشف ودرجات خطر تجريبية، وليس نظامًا طبيًا مثبتًا للتنبؤ**.

## 8. الإشعارات والطوارئ: لا تخلط الإنشاء بالتسليم

- توجد طبقة FCM حقيقية في الخادم، مع إزالة tokens غير الصالحة وإعادة محاولة أخطاء عابرة. هذه ليست stub فقط في كل الأوضاع.
- `NotificationService.showLocal()` يستدعي banner داخل التطبيق؛ ليس تنفيذًا لإشعار نظام تشغيل محلي يعمل مستقلًا عن الواجهة (`mobile/lib/services/notification_service.dart:98`).
- `EmergencySmsService` يفتح محرر SMS، ويحتاج تأكيد المستخدم. نجاح `launchUrl` لا يثبت إرسال الرسالة أو وصولها (`mobile/lib/services/emergency_sms_service.dart:7` و`:46`).
- FCM notification payload قد يعرضه النظام في الخلفية؛ عدم اختبار handler أو جهاز حقيقي هنا لا يبرر الجزم بأن كل إشعارات الخلفية تفشل. المطلوب اختبار end-to-end فعلي.
- اجعل حالات الحدث منفصلة: `detected → persisted → queued → provider_accepted → acknowledged → resolved/escalated`. لا تعرض «تم إنقاذ/إبلاغ المرافق» لمجرد فتح composer أو نجاح طلب HTTP.

## 9. الجوانب الجيدة التي يُبنى عليها

1. أدوار JWT وفحوص وصول المريض وربط الجهاز وهويته موجودة وليست واجهة شكلية فقط.
2. حفظ bundle وoutbox في معاملة واحدة موجود فعليًا في مسار cloud store، مع منع تضارب معرفات البيانات بين المرضى.
3. فحوص finite values وطول النافذة والتوقيت وجودة بعض الإشارات موجودة في أجزاء من المسار؛ المطلوب تعميم العقد لا إلغاؤه.
4. Alembic ودعم SQLite/PostgreSQL واختبارات ترحيل وعامل outbox ومقاييس تشغيل أساس جيد.
5. SQLCipher على Android/iOS وتخزين JWT ومفتاح القاعدة في SecureStore نقاط إيجابية، رغم الثقوب في الكاش والبصمة ومعالجة فشل الخزنة.
6. توجد CI لـ backend وPostgreSQL وFlutter وبناء اللوحة. لكن lint/analyze تحذيريان، ولا توجد تغطية end-to-end كافية للسيناريوهات أعلاه. إعداد job في YAML ليس دليلًا أن آخر تشغيل له نجح.

## 10. خطة إصلاح مرتبة ومعايير قبول

### المرحلة أ — احتواء الأمان وفصل العرض التجريبي

- تدوير المفتاح المحتمل تسريبه، وإزالة الأسرار الثابتة وإضافة secret scanning.
- منع demo seeding وfallback التجريبي وتوليد القياسات في إصدار الإنتاج.
- إصلاح ربط الأدوار وتعطيل العلاقات، ومراجعة العلاقات والحسابات الموجودة.
- إزالة كلمات المرور من SharedPreferences، وعزل كاش المستخدمين والبيئات.

**معيار القبول:** startup إنتاج نظيف لا ينشئ حسابات عرض؛ كل محاولات ربط دور غير caregiver مرفوضة؛ تسجيل الخروج/تبديل الحساب لا يكشف كاش سابق؛ لا توجد كلمات مرور مخزنة نصيًا.

### المرحلة ب — جعل مسار الخطر كاملًا ومستقلًا

- ربط ingestion بالحفظ والمعاملة وoutbox، مع معرف نافذة/حدث ثابت ومصدر القياس.
- ضبط freshness/TTL/quality؛ ومنع أي pre-alert لتوقع غير صالح أو من مريض آخر.
- إصلاح تجديد JWT ومعدل نقل الجهاز، وحجز عناصر outbox قبل التسليم المتزامن.
- الحفاظ على هويات FCM الأصلية وتصميم الإقرار والتصعيد بوضوح.

**معيار القبول:** نافذة خطر تُحفظ ويصل قصد إشعارها إلى المرسل الاختباري دون تطبيق هاتف؛ retry لا ينشئ حدثًا جديدًا؛ انقطاع الجهاز ظاهر؛ انتهاء JWT لا يوقف الجلسة؛ restart لا يفقد حدثًا سبق تأكيد حفظه.

### المرحلة ج — اتساق البيانات وعقود API

- معاملة إنشاء المريض؛ Pydantic schemas؛ عدم استبدال الاسم؛ projection زمني صحيح.
- جدول وصفات أو concurrency control؛ outbox للتقييمات غير الحرجة.
- تنفيذ/تعطيل موارد الرعاية غير المدعومة؛ عزل 404؛ إصلاح UTC و201.
- فصل مسارات SPA/API، واستبدال SSO عبر query، وفحص إعدادات المصادقة الحيوية.

**معيار القبول:** اختبار تكامل من العميل إلى API يثبت round-trip لكل عملية؛ لا نجاح جزئي ولا فقد عند التزامن أو reconnect؛ الروابط المباشرة للإدارة تعمل؛ واجهات غير منفذة لا توهم المستخدم بالمشاركة السحابية.

### المرحلة د — قابلية التشغيل والإثبات البحثي

- مراجعة Supabase grants/RLS والنسخ الاحتياطي واستعادة البيانات وسياسة الاحتفاظ.
- E2E على أجهزة Android/iOS: خلفية/تطبيق مغلق/رفض أذونات/شبكة ضعيفة/تغيير حساب.
- تثبيت نسخ الأدوات والاعتماديات القابلة لإعادة البناء؛ استخدام lockfile للوحة بدل افتراض غيابه؛ وإضافة اختبار المحاكي لمسار CI.
- تقليل مسؤوليات `AppState`، وتوحيد DTOs والعملاء من OpenAPI، دون إعادة كتابة شاملة قبل إصلاح العيوب المثبتة.
- تنفيذ بروتوكول التقييم البحثي المستقل قبل نشر أي نسبة حساسية أو زمن تنبؤ للمستخدمين.

## 11. اختبارات الانحدار التي يجب تحويل النتائج إليها

- production startup بدون حسابات تجريبية، حتى خارج pytest.
- منع كل اقترانات الأدوار غير الصحيحة، ومنع تعطيل حساب عالمي عبر علاقة مريض.
- ingestion → حفظ → outbox دون هاتف؛ repeat/reorder/restart وانتهاء JWT.
- إشارة غير صالحة أو قديمة أو مريض جديد تمسح توقع السياق السابق ولا تطلق إنذارًا.
- reconnect يرسل القراءة والتقييم معًا؛ 404 لميزة غير منشورة لا يحجز acknowledgment.
- إنشاء مريض يتراجع بالكامل عند الفشل؛ وصفتان متزامنتان تبقيان محفوظتين.
- توقيت محلي يُرسل UTC ويقبله الخادم؛ استجابة 201 تُعد نجاحًا.
- فصل sessions والكاش والبصمة وإشعارات FCM؛ عدم إضاعة patient_id/alert_id.
- rate budget يطابق معدل العينات المستمر؛ وقياس HR لا يتغير بسبب fs ضمني خاطئ.
- عقد موحد بين OpenAPI وعملاء Dart/JavaScript، واختبارات متصفح/native لا يحققها build وحده.
