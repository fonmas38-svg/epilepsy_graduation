# خطة التنبيهات في الخلفية — Foreground Service + Firebase

**الهدف:** أن يصل التنبيه للمريض وأسرته **حتى لو أُغلق التطبيق**، مع الإبقاء على
مسارين مستقلين (FCM + خدمة محلية) بحيث يكفي أحدهما إن تعطّل الآخر.

**النطاق:** `mobile/` فقط + تعديلات صغيرة في `backend/` لدعم `alert_id` والتأكيد.
لا مساس بالنموذج ولا بالمحاكي.

---

## 1) المشكلة الحالية

قرأنا كود التطبيق، وهذه حالته:

| البند | الحالة |
|---|---|
| `firebase_messaging` | مضاف، ويستقبل الإشعار في المقدمة والخلفية |
| إشعار محلي | `flutter_local_notifications` مضاف |
| التطبيق مُغلق تمامًا (swiped away) | **لا يوجد ضمان** — Android يقتل العملية، وعلى أجهزة Xiaomi/Huawei/Oppo تُقتل حتى رسائل FCM ذات الأولوية العالية |
| ويندوز | `firebase_messaging` **لا يدعم ويندوز** — لا تنبيه إطلاقًا |
| ازدواج التنبيه | لا يوجد منع للتكرار — إن وصل التنبيه من مسارين يظهر مرتين |
| فقد الاتصال | لا توجد آلية لاسترجاع التنبيهات الفائتة عند العودة |

النتيجة: التنبيه — وهو **جوهر المشروع** — غير مضمون في السيناريو الأخطر: المريض
نائم والتطبيق مُغلق.

---

## 2) المعمارية المقترحة: ثلاث طبقات متوازية

```
                        ┌─────────────────────────┐
                        │   Backend (FastAPI)     │
                        │   يُنتج alert_id فريد    │
                        └───────┬─────────┬───────┘
                     FCM push   │         │  HTTP polling
                                ▼         ▼
   ┌────────────────────────────────────────────────────────┐
   │                     تطبيق Flutter                       │
   │  ┌──────────────┐  ┌──────────────────┐  ┌───────────┐ │
   │  │ الطبقة 1     │  │ الطبقة 2         │  │ الطبقة 3  │ │
   │  │ FCM          │  │ Foreground Svc   │  │ Local     │ │
   │  │ (Android/iOS)│  │ (Android)        │  │ Notifs    │ │
   │  └──────┬───────┘  └────────┬─────────┘  └─────┬─────┘ │
   │         └───────────┬───────┘                  │       │
   │                     ▼                          │       │
   │            AlertDedupeStore (alert_id)  ────────┘       │
   │                     │                                  │
   │                     ▼                                  │
   │            إشعار واحد + صوت + اهتزاز                    │
   └────────────────────────────────────────────────────────┘
```

**المبدأ:** كل طبقة تعمل مستقلة، وكلها تمر عبر **بوابة منع التكرار** الموحدة، فلا
يرى المستخدم أكثر من إشعار واحد لكل حدث.

## 3) الطبقة 1 — FCM (موجودة، تحتاج تقوية)

| البند | المطلوب |
|---|---|
| نوع الرسالة | **data-only** لا `notification` — لنتحكم بالعرض بأنفسنا ونضمن استدعاء المعالج |
| الأولوية | `high` + `apns-priority: 10` |
| `content_available` | `true` على iOS |
| الحقول | `alert_id`, `severity`, `probability`, `lead_time_min`, `patient_id`, `created_at` |
| `collapse_key` | `alert_id` — يمنع تكرار نفس الحدث من جهة الخادم |
| TTL | قصير (5 دقائق) — تنبيه قديم لا قيمة له وقد يُربك |
| معالج الخلفية | `@pragma('vm:entry-point')` مع تسجيل مبكر قبل `runApp` |

**قيد يجب توثيقه:** على أجهزة MIUI/EMUI/ColorOS مع تقييد البطارية العدواني، قد لا
يصل FCM حتى بأولوية عالية. لهذا **الطبقة 2 ليست ترفًا**.

---

## 4) الطبقة 2 — Foreground Service (Android) — الجديد

### 4.1 لماذا Foreground Service تحديدًا

بديلان مرفوضان:
- `WorkManager`: أدنى دورية **15 دقيقة**، وقد تتأخر أكثر. غير مقبول لتنبيه نوبة.
- `AlarmManager` وحده: تقييدات Doze تجعله غير موثوق للاستقصاء المتكرر.

Foreground Service بإشعار دائم هو الطريقة **الوحيدة المدعومة رسميًا** لعمل مستمر
موثوق على Android الحديث، وهو ما تفعله تطبيقات الملاحة والتتبع الصحي.

### 4.2 المواصفات

| البند | القيمة |
|---|---|
| الحزمة المقترحة | `flutter_foreground_task` |
| نوع الخدمة (Android 14+) | `health` — الأنسب دلاليًا ويقبله متجر Play لهذا الاستخدام |
| الإشعار الدائم | «مراقبة نشطة» + آخر وقت تحقق + حالة الاتصال |
| دورية الاستقصاء | **15 ثانية** افتراضيًا، قابلة للضبط (10–60 ثانية) |
| نقطة النهاية | `GET /alerts/pending?since=<ts>` |
| عند اكتشاف تنبيه | إشعار كامل + صوت + اهتزاز عبر بوابة منع التكرار |
| استمرار بعد إعادة التشغيل | `RECEIVE_BOOT_COMPLETED` + إعادة تشغيل تلقائية |
| التحكم | المريض يستطيع تشغيل/إيقاف المراقبة من الإعدادات |

### 4.3 الأذونات المطلوبة

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_HEALTH" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.WAKE_LOCK" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS" />
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM" />
```

### 4.4 ترشيد استهلاك البطارية

استقصاء كل 15 ثانية على مدار الساعة يستهلك البطارية. حلول مدمجة:

| الحالة | الدورية |
|---|---|
| جهاز EEG متصل ونشط | 15 ثانية |
| الجهاز غير متصل | 60 ثانية |
| المراقبة موقوفة يدويًا | الخدمة متوقفة |
| بطارية الهاتف < 15% ولا شحن | 60 ثانية + إشعار للمستخدم |
| لا شبكة | backoff تدريجي حتى 120 ثانية، ثم استئناف فوري عند العودة |

نعرض للمستخدم صراحة أن المراقبة المستمرة تستهلك بطارية أكثر، مع خيار الضبط.

### 4.5 معالجة تقييد الشركات المصنّعة

عند أول تشغيل، إن كان الجهاز من شركة معروفة بالتقييد (Xiaomi/Huawei/Oppo/Vivo/
Samsung)، نعرض شاشة إرشادية تشرح:
- استثناء التطبيق من تحسين البطارية
- تفعيل «التشغيل التلقائي» (Autostart)
- تثبيت التطبيق في قائمة المهام الحديثة (Lock in recents)

مع زر ينقل المستخدم مباشرة لشاشة الإعدادات المعنية. هذه خطوة لا يمكن تجاوزها
برمجيًا، والحل الوحيد إرشاد المستخدم.

## 5) الطبقة 3 — ويندوز

`firebase_messaging` لا يدعم ويندوز. البديل داخل التطبيق نفسه:

| البند | القيمة |
|---|---|
| المسار | استقصاء دوري داخل عملية التطبيق (Timer) |
| الدورية | 15 ثانية |
| الإشعار | `local_notifier` أو `windows_notification` (Toast أصلي) |
| الصوت | `audioplayers` لصوت تنبيه متكرر |
| النافذة | إحضار النافذة للمقدمة + وميض في شريط المهام عبر `window_manager` |
| القيد | يعمل فقط أثناء تشغيل التطبيق — نوثّقه بوضوح ولا ندّعي غير ذلك |

ويندوز منصة عرض/إشراف (الطبيب، لوحة المتابعة) لا منصة المريض المحمولة، فالقيد مقبول.

## 6) بوابة منع التكرار (Deduplication) — إلزامية

بدونها سيظهر التنبيه مرتين أو ثلاثًا. القاعدة:

```
عند وصول تنبيه من أي مسار:
  1) اقرأ alert_id
  2) إن وُجد في المخزن المحلي (آخر 200 معرّف) → تجاهل تمامًا
  3) وإلا → اعرض الإشعار + أضف المعرّف للمخزن مع الطابع الزمني
  4) نظّف المعرّفات الأقدم من 24 ساعة
```

| البند | القيمة |
|---|---|
| التخزين | Hive أو `shared_preferences` (يعمل من معالج الخلفية) |
| السعة | آخر 200 `alert_id` أو 24 ساعة، أيهما أسبق |
| معرّف الإشعار | مشتق من `alert_id` (hash) — يضمن أن استدعاءين ينتجان إشعارًا واحدًا |

**متطلب من الباك:** كل تنبيه يجب أن يحمل `alert_id` **ثابتًا** يُرسل عبر كل المسارات
(FCM + polling). إن اختلف المعرّف بين المسارين تنهار البوابة.

## 7) قنوات الإشعارات ومستويات الخطورة

| القناة | الأهمية | الصوت | الاهتزاز | الاستخدام |
|---|---|---|---|---|
| `alerts_critical` | `max` | مخصص متكرر | نمط طويل | خطورة عالية — يتجاوز وضع عدم الإزعاج |
| `alerts_high` | `high` | مخصص | نمط قصير | خطورة متوسطة |
| `alerts_info` | `default` | افتراضي | لا | معلوماتي |
| `monitoring_service` | `low` | لا | لا | الإشعار الدائم للخدمة |

للخطورة العالية: `fullScreenIntent` لعرض شاشة التنبيه فوق شاشة القفل — المريض
النائم لا يرى شريط الإشعارات.

**استثناء عدم الإزعاج:** نطلب `ACCESS_NOTIFICATION_POLICY` ونشرح للمستخدم أن
تنبيهات النوبة يجب أن تتجاوز الصامت، مع إبقاء القرار له.

## 8) تسليم مضمون: استرجاع الفائت

عند فتح التطبيق أو عودة الشبكة:

```
GET /alerts/pending?since=<آخر alert_id مستلم>
```

- إن وُجدت تنبيهات فائتة **خلال آخر 30 دقيقة** → تُعرض مع وسم «متأخر».
- الأقدم من 30 دقيقة → تُضاف للسجل بلا إشعار (لا قيمة لتنبيه قديم).
- التطبيق يرسل تأكيد استلام: `POST /alerts/{id}/ack` → نعرف من الباك أي تنبيه لم
  يُستلم فنعيد الإرسال أو نصعّد لمُتلقٍّ آخر (الأسرة، الطبيب).

هذه الحلقة (ack) هي ما يحوّل النظام من «أرسلنا» إلى «وصل فعلًا».

---

## 9) تعديلات الباك المطلوبة (صغيرة ومحصورة)

| التعديل | الوصف |
|---|---|
| `alert_id` ثابت | معرّف فريد يُولَّد مرة ويُستخدم في FCM وpolling معًا |
| `GET /alerts/pending` | تنبيهات غير مؤكدة الاستلام، مع `since` |
| `POST /alerts/{id}/ack` | تأكيد استلام من الجهاز، مع `device_id` |
| `collapse_key` في FCM | يساوي `alert_id` |
| رسائل data-only | إزالة حِمل `notification` من رسالة FCM |
| تصعيد عند عدم التأكيد | إن لم يصل ack خلال 60 ثانية → إشعار الأسرة/الطبيب |

كلها في طبقة التنبيهات، **لا علاقة لها بالنموذج أو المحاكي**.

## 10) الاختبار

| السيناريو | المتوقع |
|---|---|
| التطبيق في المقدمة | إشعار فوري مرة واحدة |
| التطبيق في الخلفية | إشعار فوري مرة واحدة |
| التطبيق مُغلق (swiped) | الخدمة تكتشف خلال ≤ 15 ثانية |
| الهاتف مقفل والشاشة مطفأة | إشعار + صوت + شاشة كاملة |
| وضع الطيران ثم عودة الشبكة | استرجاع الفائت خلال ≤ 30 ثانية |
| FCM + polling يصلان معًا | **إشعار واحد فقط** |
| إعادة تشغيل الهاتف | الخدمة تعود تلقائيًا |
| وضع Doze | الخدمة تستمر (اختبار عبر `adb shell dumpsys deviceidle force-idle`) |
| ويندوز والتطبيق مفتوح | Toast + صوت + إحضار النافذة |

اختبارات آلية مطلوبة: بوابة منع التكرار (وحدة)، حساب دورية الاستقصاء (وحدة)،
استرجاع الفائت (تكامل).

## 11) خطوات التنفيذ

1. `AlertDedupeStore` + قنوات الإشعارات (أساس كل ما بعده)
2. `GET /alerts/pending` + `POST /alerts/{id}/ack` + `alert_id` في الباك
3. `AlertGateway` موحّد في Flutter تمر منه كل المسارات
4. Foreground Service على Android + الأذونات + العودة بعد الإقلاع
5. إشعارات ويندوز + الاستقصاء داخل العملية
6. ترشيد البطارية + شاشة إرشاد الشركات المصنّعة
7. تحويل FCM إلى data-only + `collapse_key`
8. تصعيد عند عدم التأكيد
9. الاختبارات + التوثيق

---

## 12) قيود نوثّقها بصراحة

- **ويندوز:** لا تنبيه عند إغلاق التطبيق. لا حل ضمن Flutter بلا خدمة نظام مستقلة.
- **iOS:** لا مقابل لـForeground Service. نعتمد FCM + Critical Alerts (تحتاج
  موافقة Apple خاصة). الدعم أضعف من Android بحكم النظام.
- **الشركات المقيّدة:** لا ضمان 100% بلا تدخل المستخدم في الإعدادات.
- **البطارية:** المراقبة المستمرة تستهلك أكثر. نعرض ذلك للمستخدم بلا مواربة.

هذه ليست نواقص تنفيذ بل حدود المنصات. نذكرها في دليل المستخدم وفي المشروع، لأن
إخفاءها في تطبيق طبي أخطر من وجودها.
