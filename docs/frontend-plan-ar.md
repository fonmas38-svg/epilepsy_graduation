# خطة Frontend المتكاملة — نظام التنبؤ المبكر بنوبات الصرع

**النطاق:** تطبيق Flutter (مريض / أسرة / طبيب) + لوحة إدارة React (مدير النظام).
**القيد الأساسي:** لا تعديل على النموذج ولا على المحاكي. كل ما هنا يعمل فوق
الـAPI الحالي أو بإضافات محصورة في طبقة العرض والتنسيق.

**مستندات مرتبطة:**
`docs/model-requirements-ar.md` · `docs/hosting-request-ar.md` ·
`docs/background-alerts-ar.md` · `docs/api.md` · `docs/ADMIN_SYSTEM.md`

---

## 1) الوضع الحالي — تقييم صريح

### 1.1 تطبيق Flutter

| الجانب | الحالة |
|---|---|
| الأدوار المدعومة | مريض + طبيب (جزئي) |
| دور الأسرة | **غير موجود كواجهة مستقلة** |
| الشاشات | تسجيل دخول، لوحة المريض، سجل، إعدادات، شاشة طبيب مبسطة |
| إدارة الحالة | مختلطة — `setState` + بعض الـProviders، بلا نمط موحّد |
| التعريب | نصوص عربية **مكتوبة داخل الكود مباشرة** (hardcoded) |
| RTL | غير مضبوط بالكامل — بعض العناصر تُعرض LTR |
| الوضع الليلي | غير موجود |
| إمكانية الوصول | غير مُعالجة (أحجام خطوط، تباين، قارئ شاشة) |
| العمل دون اتصال | غير موجود — أي انقطاع = شاشة فارغة |
| معالجة الأخطاء | رسائل تقنية خام تظهر للمستخدم |
| الاختبارات | شبه معدومة |

### 1.2 لوحة الإدارة React

| الجانب | الحالة |
|---|---|
| الوظائف | إدارة مستخدمين أساسية، عرض تنبيهات |
| التصميم | بدائي، بلا نظام تصميم موحّد |
| اللغة | إنجليزي غالبًا، بلا تعريب |
| المراقبة التشغيلية | غير موجودة |
| إدارة النموذج | غير موجودة |

### 1.3 الخلاصة

الواجهة الحالية **نموذج أولي يثبت أن الـAPI يعمل**، لا منتج. الفجوة الأكبر:
- لا واجهة لأفراد الأسرة — وهم **المستفيد الأهم عمليًا** (المريض أثناء النوبة لا
  يستطيع استخدام هاتفه).
- لا عمل دون اتصال — وهو أمر حرج في تطبيق يُفترض أن يعمل 24/7.
- لا تعريب منظّم — يستحيل التوسع أو المراجعة.

## 2) الأسس التقنية (Foundation) — قبل أي شاشة جديدة

هذه ليست «تحسينات»، بل أرضية بدونها يتحول كل ما بعدها إلى دَين تقني.

### 2.1 إدارة الحالة

**الاختيار: Riverpod**

| السبب | التفصيل |
|---|---|
| اختبارية | يمكن استبدال أي provider في الاختبار بلا bootstrapping |
| أمان النوع | أخطاء وقت الترجمة لا وقت التشغيل |
| مناسب لبيانات حية | `StreamProvider` + `AsyncValue` يعالج loading/error/data بنمط واحد |
| لا يحتاج BuildContext | يعمل من الخدمات الخلفية والمعالجات |

**بنية الطبقات:**
```
lib/
├── core/            # ثوابت، أخطاء، امتدادات، تهيئة
├── data/
│   ├── api/         # عملاء HTTP لكل مورد
│   ├── models/      # نماذج البيانات (freezed + json_serializable)
│   ├── local/       # تخزين محلي (Drift/Hive)
│   └── repositories/# منطق الدمج بين البعيد والمحلي
├── domain/          # الكيانات وحالات الاستخدام
├── presentation/
│   ├── patient/     # شاشات المريض
│   ├── family/      # شاشات الأسرة
│   ├── doctor/      # شاشات الطبيب
│   ├── shared/      # مكونات مشتركة
│   └── router/      # التوجيه
└── l10n/            # ملفات الترجمة
```

### 2.2 التوجيه

**go_router** مع حراسة قائمة على الدور:

| القاعدة | السلوك |
|---|---|
| مستخدم غير مصادَق | إعادة توجيه إلى `/login` |
| دور غير مطابق للمسار | إعادة توجيه إلى الجذر الخاص بدوره |
| Deep link من إشعار | `/alerts/{alert_id}` يفتح التنبيه مباشرة |
| حفظ آخر مسار | العودة إليه بعد إعادة تشغيل التطبيق |

### 2.3 التعريب (i18n) — إلزامي قبل أي شاشة جديدة

- `flutter_localizations` + ملفات ARB.
- **لا نص عربي داخل الكود.** كل نص عبر `AppLocalizations`.
- دعم `ar` (أساسي) و`en` (ثانوي).
- ضبط `Directionality` تلقائيًا حسب اللغة.
- تنسيق التواريخ والأرقام بـ`intl` مع التقويم الهجري كخيار.

**سبب الأولوية:** إن أضفنا 20 شاشة بنصوص مضمّنة، فتعريبها لاحقًا يعني تعديل كل
ملف. الترتيب الصحيح: البنية أولًا.

### 2.4 نظام التصميم

| العنصر | القرار |
|---|---|
| الأساس | Material 3 مع ثيم مخصص |
| الألوان | لوحة دلالية: `safe` (أخضر)، `caution` (كهرماني)، `danger` (أحمر)، `unknown` (رمادي) |
| الخط | Cairo أو IBM Plex Sans Arabic — وضوح عالٍ بالعربية |
| الوضع الليلي | إلزامي — المريض قد يفتح التطبيق ليلًا وشاشة بيضاء ساطعة مؤذية |
| المسافات | مقياس 4pt |
| المكونات | مكتبة موحّدة: `RiskGauge`, `AlertCard`, `SignalChart`, `StatusBadge`, `EmptyState`, `ErrorState`, `LoadingSkeleton` |

**قاعدة حرجة في الألوان:** لا نعتمد على اللون وحده لنقل الخطورة. كل حالة تحمل
**لونًا + أيقونة + نص**. نسبة معتبرة من الذكور مصابون بعمى ألوان، وأحمر/أخضر أسوأ
اختيار ممكن للاعتماد عليه منفردًا في تطبيق طبي.

### 2.5 العمل دون اتصال

| المكوّن | القرار |
|---|---|
| قاعدة محلية | **Drift** (SQLite) — استعلامات مكتوبة بأمان النوع |
| ما يُخزَّن | السجل، الأدوية، جهات الاتصال، آخر حالة، خطة الطوارئ |
| ما لا يُخزَّن | الإشارة الخام (حجم كبير بلا فائدة) |
| المزامنة | طابور صادر (outbox) مع إعادة محاولة عند العودة |
| المؤشر | شريط علوي «غير متصل — آخر تحديث قبل X» |

**قاعدة:** أي شاشة **يجب** أن تعرض شيئًا مفيدًا دون اتصال. خطة الطوارئ وجهات
الاتصال يجب أن تعمل بلا شبكة إطلاقًا — وقت الحاجة إليها هو أسوأ وقت للاعتماد على
الاتصال.

### 2.6 معالجة الأخطاء

| النوع | ما يراه المستخدم |
|---|---|
| انقطاع شبكة | «لا يوجد اتصال. سنحاول تلقائيًا» + زر إعادة |
| مهلة انتهت | «الخادم بطيء الاستجابة» + إعادة |
| 401 | تجديد الجلسة صامتًا، وإن فشل: تسجيل خروج مع تفسير |
| 403 | «لا تملك صلاحية لهذا الإجراء» |
| 5xx | «خلل مؤقت لدينا، لا علاقة له ببياناتك» |

لا رسائل تقنية ولا أكواد خام. السجل التقني يذهب للـlogs لا لعين المستخدم.

## 3) واجهة المريض

### 3.1 الشاشة الرئيسية — «حالتي الآن»

العنصر المركزي: **مؤشر الحالة**.

| المستوى | اللون | الأيقونة | النص |
|---|---|---|---|
| آمن | أخضر | ✓ درع | «الوضع مستقر» |
| انتباه | كهرماني | ⚠ مثلث | «ارتفاع طفيف — كن قريبًا من مكان آمن» |
| تحذير | أحمر | ⛔ دائرة | «احتمال مرتفع خلال ~X دقيقة» |
| غير معروف | رمادي | ? | «لا توجد بيانات كافية» |

**قاعدة تصميم حاسمة:** حين لا يعمل النموذج أو ينقطع الجهاز، **لا نعرض «آمن»**.
نعرض «غير معروف» صراحة. عرض الأخضر بلا بيانات كذبة قد تكلّف المريض حياته، وهي
أخطر خطأ يمكن ارتكابه في هذا التطبيق.

**بقية العناصر:**
- زر **«أحتاج مساعدة»** كبير وثابت — يُنبّه الأسرة فورًا، ويعمل بلمسة واحدة.
- حالة الجهاز: متصل/غير متصل، البطارية، جودة الإشارة، آخر تحديث.
- بطاقة الدواء التالي مع زر «تناولته».
- شريط زمني مبسّط لآخر 12 ساعة.

### 3.2 شاشة التنبيه النشط

تفتح تلقائيًا عند تنبيه عالي الخطورة، حتى فوق شاشة القفل.

| العنصر | الوصف |
|---|---|
| العنوان | «احتمال نوبة خلال ~10 دقائق» |
| عدّاد | تنازلي مرئي |
| خطوات فورية | 3 خطوات قصيرة: اجلس في مكان آمن، أبلغ من حولك، ابتعد عن الدرج/الماء |
| أزرار | «أنا بخير» · «أحتاج مساعدة» · «تنبيه خاطئ» |
| إشعار الأسرة | يظهر من تم إبلاغه ومن استجاب |

زر **«تنبيه خاطئ»** ليس تفصيلًا — هو مصدر بيانات حقيقي لقياس دقة النظام في
الاستخدام الفعلي، ويعطي المريض شعورًا بالسيطرة بدل الانفعال السلبي.

### 3.3 السجل والتحليلات

- خط زمني للأحداث: تنبيهات، نوبات مؤكدة، أدوية، ملاحظات.
- **تقويم شهري** بترميز لوني لكثافة الأحداث.
- إحصاءات: عدد النوبات شهريًا، متوسط زمن الاستباق، نسبة الإنذارات الخاطئة.
- **مذكرات محفزات (triggers)**: نوم، ضغط، إجهاد، وجبات، دورة شهرية، حمّى.
- ربط بصري بين المحفزات والأحداث — **بلا ادعاء سببية**. نعرض تزامنًا ونقول ذلك
  صراحة: «لوحظ تزامن» لا «سبب».
- تصدير PDF لعرضه على الطبيب.

### 3.4 إدارة الأدوية

| الميزة | التفصيل |
|---|---|
| جدول الجرعات | باسم الدواء والجرعة والتوقيت |
| تذكير | إشعار في وقت الجرعة |
| تتبع الالتزام | نسبة الالتزام أسبوعيًا وشهريًا |
| تنبيه نفاد | «تبقى 5 أيام من الدواء» |
| ربط بالأحداث | عرض الجرعات الفائتة قرب النوبات |
| مشاركة | الطبيب يرى نسبة الالتزام |

عدم الالتزام الدوائي من أكثر أسباب تكرار النوبات شيوعًا. هذه الشاشة قد تكون أنفع
للمريض من النموذج نفسه.

### 3.5 خطة الطوارئ

- تعمل **دون اتصال بالكامل** — أهم متطلب فيها.
- جهات اتصال مرتبة بالأولوية، اتصال بضغطة واحدة.
- بطاقة طبية: التشخيص، الأدوية، الحساسية، فصيلة الدم، الطبيب المعالج.
- تعليمات الإسعاف لمن حول المريض — بلغة بسيطة وبالصور.
- شاشة قفل طبية: عرض المعلومات الحيوية دون فتح الهاتف.

### 3.6 إعدادات المريض

- الحساسية: منخفضة / متوسطة / عالية، مع شرح المقايضة بلغة مفهومة:
  «حساسية أعلى = تنبيه أبكر + إنذارات خاطئة أكثر».
- ساعات الهدوء (لكن تنبيهات الخطورة العالية تتجاوزها دائمًا).
- من يُبلَّغ عند كل مستوى خطورة.
- الخصوصية: من يرى ماذا، وإيقاف المشاركة.
- **تصدير بياناتي** و**حذف حسابي** — حق أصيل للمستخدم في أي نظام صحي.

## 4) واجهة الأسرة — الأهم عمليًا

المريض أثناء النوبة **لا يستطيع** استخدام هاتفه. لذلك واجهة الأسرة ليست ميزة
ثانوية، بل قناة الاستجابة الفعلية.

### 4.1 الشاشة الرئيسية

- بطاقة لكل مريض مرتبط (قد يتابع الشخص أكثر من فرد).
- حالة مباشرة: مستوى الخطورة، حالة الجهاز، آخر تحديث.
- الموقع الحالي **بإذن صريح من المريض** وقابل للإيقاف.
- سجل مختصر لآخر الأحداث.

### 4.2 شاشة الاستجابة للتنبيه

| العنصر | الوصف |
|---|---|
| الحالة | من التنبيه إلى الآن |
| موقع المريض | خريطة + زر «الاتجاهات» |
| أزرار سريعة | اتصال · رسالة · «أنا في الطريق» |
| حالة الأسرة | من رأى التنبيه، من استجاب، من في الطريق |
| تعليمات الإسعاف | خطوات مصوّرة أثناء النوبة |
| توثيق | تسجيل مدة النوبة ونوعها بعد انتهائها |

**تنسيق الاستجابة** (من استجاب) يمنع مشكلتين: أن يظن الجميع أن غيره ذاهب، أو أن
يذهب الجميع دفعة واحدة.

### 4.3 صلاحيات وخصوصية الأسرة

نموذج صلاحيات متدرج يقرره **المريض**:

| المستوى | ما يراه |
|---|---|
| تنبيهات فقط | التنبيهات العاجلة لا غير |
| مراقبة أساسية | + الحالة الحالية وحالة الجهاز |
| مراقبة كاملة | + السجل والأدوية |
| وصي (قاصر) | كل شيء + صلاحية التعديل |

- **موافقة المريض إلزامية** لربط أي فرد أسرة (عدا حالة القاصر بولاية موثقة).
- المريض يستطيع سحب الصلاحية في أي وقت بلا تبرير.
- سجل وصول شفاف: من اطّلع على ماذا ومتى — يراه المريض.

هذا ليس تعقيدًا زائدًا. تطبيق يعرض موقع شخص بالغ وحالته الصحية لأقاربه بلا إذنه
ينتهك خصوصيته، وقد يتحول إلى أداة تحكم بدل أن يكون أداة حماية.

## 5) واجهة الطبيب

### 5.1 قائمة المرضى

- جدول قابل للفرز مع فرز افتراضي حسب **الحاجة للانتباه**.
- مؤشرات سريعة: تنبيهات آخر 7 أيام، الالتزام الدوائي، حالة الجهاز.
- تصفية: مرضى بتنبيهات جديدة، بأجهزة معطلة، بالتزام منخفض.
- بحث بالاسم أو رقم الملف.

### 5.2 ملف المريض

| القسم | المحتوى |
|---|---|
| ملخص | التشخيص، الأدوية، تاريخ النوبات، آخر زيارة |
| الخط الزمني | تنبيهات ونوبات وأدوية على محور واحد |
| الإشارة | عرض نافذة الإشارة حول أي حدث |
| التحليلات | تكرار، أنماط زمنية، ارتباط بالمحفزات |
| الملاحظات السريرية | ملاحظات الطبيب، خاصة به |
| الإعدادات | ضبط الحساسية والأفق لهذا المريض |

### 5.3 ضبط الحساسية لكل مريض

الطبيب يختار من **نقاط التشغيل** التي يسلّمها فريق النموذج:

| النقطة | الحساسية | إنذارات كاذبة/ساعة |
|---|---|---|
| متحفظ | 0.71 | 0.18 |
| متوازن | 0.84 | 0.45 |
| حساس | 0.92 | 1.10 |

نعرض الأثر المتوقع بلغة سريرية: «هذا الإعداد يعني تنبيهًا خاطئًا كل ~5 ساعات».

### 5.4 مراجعة الأحداث (Adjudication)

الطبيب يؤكد لكل تنبيه: **نوبة حقيقية / إنذار كاذب / غير محدد**.

هذه أهم ميزة في واجهة الطبيب. منها:
- نحسب دقة النظام **الحقيقية** في الاستخدام الفعلي لا في مجموعة الاختبار.
- نبني بيانات لتحسين النموذج مستقبلًا.
- نعطي المريض ثقة مبنية على مراجعة بشرية.

**لا نستخدم هذه البيانات لإعادة تدريب النموذج تلقائيًا.** تُجمع وتُصدَّر، وأي
إعادة تدريب تمر بمراجعة بشرية كاملة. التعلم التلقائي من تسميات غير مضبوطة في نظام
طبي طريق مباشر لتدهور صامت في الأداء.

### 5.5 التقارير

- تقرير دوري لكل مريض (PDF).
- إحصاءات إجمالية لمرضى الطبيب.
- تصدير CSV للبحث.

## 6) لوحة مدير النظام (React)

### 6.1 نظرة عامة تشغيلية

| البطاقة | المحتوى |
|---|---|
| صحة النظام | حالة الـAPI، قاعدة البيانات، النموذج، FCM |
| الأجهزة | متصلة / منقطعة / بطارية منخفضة |
| التنبيهات | آخر 24 ساعة، موزعة بالخطورة |
| الأداء | زمن الاستجابة، معدل الأخطاء، طول طابور الإرسال |
| المستخدمون | نشطون الآن، تسجيلات جديدة |

### 6.2 إدارة المستخدمين والأدوار

- إنشاء/تعطيل/حذف الحسابات (حذف ناعم مع أثر تدقيق).
- إسناد الأدوار: مريض، أسرة، طبيب، مدير.
- ربط مريض بطبيب وبأفراد أسرة.
- إعادة تعيين كلمة المرور، وفك قفل الحسابات.
- عرض جلسات المستخدم وإنهاؤها عن بُعد.

### 6.3 إدارة الأجهزة

- سجل الأجهزة وربطها بالمرضى.
- حالة كل جهاز: آخر اتصال، البطارية، إصدار البرنامج، جودة الإشارة.
- إلغاء تسجيل جهاز مفقود.
- تنبيه المدير عند انقطاع جهاز أكثر من X دقيقة.

### 6.4 إدارة النموذج

| الميزة | الوصف |
|---|---|
| النموذج النشط | الإصدار، تاريخ النشر، القنوات، الأوضاع المدعومة |
| المقاييس | حساسية، FPR/h، ECE — من `metrics.json` |
| **وضع الظل** | تشغيل نموذج مرشح بلا إرسال تنبيهات، ومقارنة نتائجه بالنشط |
| الترقية | تفعيل نموذج جديد بعد مراجعة نتائج الظل |
| التراجع | العودة للإصدار السابق بضغطة واحدة |
| سجل الإصدارات | من فعّل ماذا ومتى |

**وضع الظل** ضروري: تفعيل نموذج جديد مباشرة على مرضى حقيقيين بلا مقارنة مسبقة
مخاطرة غير مبررة. نشغّله أسبوعًا، نقارن، ثم نقرر.

### 6.5 المراقبة والسجلات

- سجل تدقيق كامل: من فعل ماذا ومتى وعلى أي مورد.
- سجل الأخطاء مع تجميع حسب النوع.
- مراقبة طابور الإرسال (outbox) ومعدل الفشل.
- تنبيهات للمدير عند: توقف الخدمة، امتلاء الطابور، ارتفاع معدل الأخطاء.

### 6.6 تحسينات تقنية للوحة

|---|---|
| المكدّس | React + TypeScript + Vite |
| البيانات | TanStack Query — تخزين مؤقت وإعادة جلب تلقائية |

## 7) إمكانية الوصول (Accessibility)

ليست بندًا تجميليًا. مرضى الصرع قد يعانون ضعف بصر أو رعاشًا أو بطء استجابة بعد
النوبة، وأفراد الأسرة قد يكونون كبار سن.

| المتطلب | التفصيل |
|---|---|
| حجم الخط | يتبع إعداد النظام، ولا تنكسر الشاشات عند 200% |
| التباين | WCAG AA كحد أدنى (4.5:1 للنص) |
| مساحة اللمس | ≥ 48×48 dp لكل عنصر تفاعلي |
| قارئ الشاشة | تسميات دلالية لكل عنصر (TalkBack/VoiceOver) |
| لا اعتماد على اللون | لون + أيقونة + نص دائمًا |
| **الحساسية للضوء** | تقليل الحركة والوميض — الحساسية الضوئية محفّز نوبات معروف |
| لغة بسيطة | لا مصطلحات تقنية في واجهة المريض والأسرة |

**بند خاص:** أي رسم متحرك سريع أو وميض **ممنوع تمامًا** في هذا التطبيق. الرسوم
تتبع إعداد «تقليل الحركة» في النظام. أن يتسبب تطبيق للتنبؤ بالنوبات في نوبة =
فشل ذريع.

## 8) الاختبارات

| النوع | التغطية المستهدفة |
|---|---|
| اختبارات وحدة | المنطق والتحويلات وبوابة منع التكرار — ≥ 70% |
| اختبارات widget | كل شاشة رئيسية في حالات: loading / error / empty / data |
| اختبارات ذهاب وإياب | 3 مسارات: تسجيل دخول → لوحة، تنبيه → استجابة، تسجيل نوبة |
| اختبار RTL | لقطات في العربية والإنجليزية |
| اختبار وصولية | التباين وأحجام اللمس آليًا |

**قاعدة:** أي شاشة تُعتبر مكتملة فقط إذا غطّت الحالات الأربع
(تحميل/خطأ/فارغ/بيانات). الشاشة التي تعمل في الحالة المثالية فقط ليست جاهزة.

## 11) مبادئ حاكمة

1. **لا تكذب على المستخدم.** غياب البيانات يُعرض «غير معروف» لا «آمن».
2. **الوضوح قبل الجمال.** المريض المذعور يحتاج معلومة واضحة لا تصميمًا أنيقًا.
3. **افترض أسوأ الظروف.** لا شبكة، بطارية منخفضة، ليل، مستخدم مرتبك.
4. **الخصوصية بالتصميم.** المريض يملك بياناته ويقرر من يراها.
5. **كل حالة معروضة.** تحميل، خطأ، فارغ، بيانات — أربعتها أو الشاشة ناقصة.
6. **العربية أولًا.** المستخدم عربي، والواجهة تُصمَّم RTL من البداية لا تُترجم لاحقًا.
7. **لا حركة مؤذية.** لا وميض ولا رسوم سريعة، احترامًا للحساسية الضوئية.
