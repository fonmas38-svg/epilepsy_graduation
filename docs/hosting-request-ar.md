# متطلبات استضافة خدمة FastAPI — مستند يُرسل لمزود الخدمة

**المشروع:** نظام تنبؤ مبكر بنوبات الصرع (مشروع تخرج).
**الطلب:** استضافة خدمة Python/FastAPI واحدة، مع قاعدة PostgreSQL على Supabase.

---

## 1) البنية المطلوبة

```
تطبيق Flutter (Android/Windows)  ┐
لوحة إدارة React                 ├──HTTPS──►  خدمة FastAPI  ──►  Supabase PostgreSQL
جهاز/محاكي إرسال البيانات        ┘            (تحتوي النموذج)
                                                    │
                                                    └──►  Firebase Cloud Messaging
```

**قرار معماري:** خدمة **واحدة** تحتوي واجهة الـAPI ونموذج الذكاء الاصطناعي معًا.
لا نطلب فصل النموذج في خدمة مستقلة؛ النموذج يُحمَّل داخل نفس عملية FastAPI.

Supabase تُستخدم كـ**PostgreSQL مُدار فقط** (اتصال عبر SQLAlchemy). لا نستخدم
Supabase Auth ولا Edge Functions ولا Storage — المصادقة والصلاحيات منفّذة داخل
FastAPI (JWT + RBAC) ومغطاة باختبارات.

---

## 2) الموارد المطلوبة

النموذج الجديد سيُسلَّم بصيغة **ONNX**، لذا لا حاجة لتثبيت PyTorch في الإنتاج.

| المورد | الحد الأدنى | الموصى به |
|---|---|---|
| vCPU | 1 | **2** |
| RAM | 1 GB | **2 GB** |
| مساحة القرص | 10 GB | **20 GB** |
| قرص دائم (Persistent volume) | 1 GB | **5 GB** |
| GPU | **غير مطلوب** | — |

> إن تعذّر ONNX واضطررنا لـPyTorch، ترتفع المتطلبات إلى **2 vCPU / 4 GB RAM /
> 20 GB قرص**. سنؤكد الصيغة النهائية قبل النشر.

**الحمل المتوقع:** مشروع تخرج بمرحلة عرض — عشرات المستخدمين، وطلب استيعاب بيانات
كل ثانية لكل جهاز نشط. لا نتوقع حملًا عاليًا.

## 3) بيئة التشغيل

| البند | القيمة |
|---|---|
| اللغة | Python **3.11** أو أحدث |
| الإطار | FastAPI + Uvicorn |
| نقطة الدخول | `backend.app.main:app` |
| المجلد الجذر للتشغيل | جذر المستودع (لأن الاستيراد بصيغة `backend.app.*`) |
| الاعتماديات | `pip install -r backend/requirements.txt` |
| المنفذ | يُقرأ من متغير البيئة `PORT` (افتراضيًا 8000) |

**أمر التشغيل:**
```bash
uvicorn backend.app.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1
```

## 4) قيد حرج: نسخة واحدة فقط (Single instance)

> **مطلوب: `workers = 1` و `replicas = 1`. من فضلكم لا تُفعّلوا التوسّع الأفقي
> التلقائي (autoscaling) لهذه الخدمة.**

السبب تقني وليس تفضيلًا:

| المكوّن | لماذا يمنع تعدد النسخ |
|---|---|
| مجمّع نوافذ الجهاز (in-memory buffer) | كل نسخة تحتفظ بجزء من عينات المريض، فتُبنى نوافذ ناقصة ويفشل التحليل |
| تحديد معدل الطلبات (rate limiting) | العدّاد في الذاكرة، فيتضاعف الحد الفعلي بعدد النسخ |
| عامل إرسال التنبيهات (outbox worker) | يعمل داخل دورة حياة التطبيق؛ نسختان = **إرسال التنبيه مرتين للمريض** |
| المقاييس التشغيلية | مجزّأة بين النسخ |

إن كان التوسّع مطلوبًا مستقبلًا، نحتاج **Redis** لنقل هذه الحالة خارج العملية،
وهذا خارج نطاق المرحلة الحالية. للمشروع الحالي: نسخة واحدة كافية تمامًا.

## 5) التخزين الدائم

| المسار | الغرض | الحجم |
|---|---|---|
| `/data/models` | أوزان النموذج (`.onnx` + `meta.json`) | ~200 MB |
| `/data/logs` | سجلات التطبيق | ~1 GB |

نمرّر مسار النموذج عبر متغير البيئة، فلا حاجة لمسار ثابت بعينه — فقط نحتاج
**قرصًا لا يُمسح عند إعادة النشر**، أو بديلًا: إمكانية تضمين ملفات النموذج داخل
صورة النشر.

## 6) قاعدة البيانات

- **PostgreSQL 14+** على Supabase.
- الاتصال عبر `DATABASE_URL` بصيغة:
  `postgresql+psycopg://USER:PASSWORD@HOST:PORT/DB?sslmode=require`
- **مطلوب `sslmode=require`** — البيانات صحية.
- نستخدم **Connection Pooler** إن كان متاحًا. نحتاج معرفة **الحد الأقصى للاتصالات
  المتزامنة** المسموح به في خطتنا لنضبط `DB_POOL_SIZE` و`DB_MAX_OVERFLOW` بما
  لا يتجاوزه (افتراضنا الحالي: pool = 5، overflow = 10).
- الترحيلات (migrations) بـAlembic، تُشغَّل **كخطوة نشر منفصلة** لا عند بدء التطبيق:
  ```bash
  alembic -c backend/alembic.ini upgrade head
  ```
- نسخ احتياطي يومي مطلوب، مع إمكانية الاستعادة الزمنية إن كانت متاحة في الخطة.

## 7) الشبكة

| البند | المطلوب |
|---|---|
| HTTPS | **إلزامي** مع شهادة صالحة وتجديد تلقائي. البيانات صحية ولا نقبل HTTP |
| اسم نطاق | نطاق فرعي ثابت يكفي (مثلًا `api-epilepsy.example.com`) |
| Egress خارجي | مطلوب إلى `fcm.googleapis.com` و`oauth2.googleapis.com` (إشعارات Firebase) |
| Egress إلى Supabase | مطلوب (منفذ 5432 أو 6543 حسب الـpooler) |
| حجم الطلب الأقصى | **1 MB** يكفي (نرسل نوافذ إشارة بصيغة JSON) |
| مهلة الطلب | ≥ 30 ثانية |
| WebSocket | غير مستخدم حاليًا. **سؤال:** هل الـproxy لديكم يدعمه، وبأي مهلة خمول؟ قد نحتاجه لبثّ الإشارة مباشرة لاحقًا |
| CORS | نضبطه داخل التطبيق عبر متغير بيئة |

## 8) فحوص الصحة (Health checks)

| المسار | الغرض | السلوك المتوقع |
|---|---|---|
| `/health/live` | هل العملية حية؟ | يعود 200 دائمًا ما دامت العملية تعمل |
| `/health/ready` | هل جاهزة لاستقبال الطلبات؟ | يفحص اتصال قاعدة البيانات وتحميل النموذج |

استخدموا `/health/live` لإعادة التشغيل التلقائي، و`/health/ready` لبوابة التوجيه.
مهلة البدء (startup grace period) المقترحة: **60 ثانية** — النموذج يحتاج وقتًا
للتحميل عند الإقلاع.

## 9) متغيرات البيئة

كلها تُضبط كمتغيرات بيئة. **الأسرار لا تُوضع في المستودع إطلاقًا.**

### إلزامية
| المتغير | الوصف |
|---|---|
| `APP_ENV` | `production` — يفعّل فحص أمان يرفض الإقلاع بأي سرّ افتراضي |
| `SECRET_KEY` | سرّ توقيع JWT (عشوائي ≥ 32 بايت) |
| `DATABASE_URL` | رابط اتصال Supabase مع `sslmode=require` |
| `ADMIN_PASSWORD` | كلمة مرور حساب المدير الأول |
| `DEVICE_ENROLL_SECRET` | سرّ تسجيل الأجهزة |
| `CORS_ORIGINS` | نطاقات لوحة الإدارة المسموحة |
| `PORT` | يوفّره المزود عادة |

### اختيارية
| المتغير | الافتراضي | الوصف |
|---|---|---|
| `RUN_MIGRATIONS_ON_STARTUP` | `0` | نُبقيها `0` ونشغّل الترحيل كخطوة نشر |
| `DB_POOL_SIZE` | `5` | حسب حد الاتصالات لديكم |
| `DB_MAX_OVERFLOW` | `10` | حسب حد الاتصالات لديكم |
| `MODEL_DIR` | `backend/models` | مسار أوزان النموذج على القرص الدائم |
| `FIREBASE_CREDENTIALS_JSON` | — | **محتوى** ملف حساب خدمة Firebase كنص JSON |
| `FIREBASE_CREDENTIALS` | — | بديل: **مسار** الملف على القرص |
| `LOG_LEVEL` | `INFO` | مستوى السجل |

> **سؤال مهم:** هل تدعم منصتكم أسرارًا **متعددة الأسطر** (مثل JSON كامل)؟ إن لم
> تدعم، سنحتاج مسار ملف على القرص الدائم بدلًا من `FIREBASE_CREDENTIALS_JSON`.

## 10) خطوات النشر المطلوبة

```bash
# 1) تثبيت الاعتماديات
pip install --no-cache-dir -r backend/requirements.txt

# 2) ترحيل قاعدة البيانات (خطوة منفصلة قبل تشغيل الخدمة)
alembic -c backend/alembic.ini upgrade head

# 3) تشغيل الخدمة (نسخة واحدة، عامل واحد)
uvicorn backend.app.main:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1
```

نستطيع توفير `Dockerfile` جاهز إن كان النشر بالحاويات أسهل لكم.

## 11) اعتبارات أمان وخصوصية

- البيانات المعالَجة **صحية وحساسة** (إشارات فسيولوجية + بيانات مرضى).
- HTTPS إلزامي في كل المسارات؛ لا نقبل نقطة نهاية HTTP حتى للاختبار.
- التشفير أثناء التخزين (encryption at rest) مطلوب لقاعدة البيانات إن كان متاحًا.
- يجب ألّا تُسجَّل محتويات الطلبات في سجلات المزوّد (قد تحتوي بيانات مرضى).
- نحتاج معرفة **الموقع الجغرافي** لمراكز البيانات لتوثيقه في المشروع.
- سياسة الاحتفاظ بالسجلات لديكم ومدتها.

## 12) أسئلتنا لكم

1. هل يمكن تثبيت **نسخة واحدة** بلا autoscaling؟ (القسم 4 — الأهم)
2. هل يتوفر **قرص دائم** لا يُمسح عند إعادة النشر؟ وما حجمه في خطتنا؟
3. ما **الحد الأقصى للاتصالات المتزامنة** مع Supabase في خطتنا؟
4. هل تدعم الأسرار متعددة الأسطر (JSON)؟
5. هل الاتصال الصادر إلى `fcm.googleapis.com` مسموح افتراضيًا؟
6. هل يدعم الـproxy **WebSocket**؟ وما مهلة الخمول؟
7. كيف تُشغَّل خطوة الترحيل (migration) قبل بدء الخدمة في منصتكم؟
8. ما آلية النشر: Git push، أم رفع صورة Docker، أم غير ذلك؟
9. أين توجد مراكز البيانات جغرافيًا؟
10. هل تشمل الخطة نسخًا احتياطيًا يوميًا لقاعدة البيانات؟

## 13) ملخص في سطور

> خدمة Python/FastAPI واحدة، **2 vCPU / 2 GB RAM / 20 GB**، بدون GPU، **نسخة
> واحدة بلا autoscaling**، مع قرص دائم صغير للنموذج، متصلة بـPostgreSQL على
> Supabase عبر SSL، خلف HTTPS، مع سماح بالاتصال الصادر إلى Firebase، وفحصا صحة
> على `/health/live` و`/health/ready`.
